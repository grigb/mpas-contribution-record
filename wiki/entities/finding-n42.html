The transport could silently resend a tool call after an auth failure

When a tool call got a 401, the MCP SDK reauthorized and repeated the request on its own, so a side effect could run twice with no new governed decision

What was wrong

examples/demo/src/adapter/dispatch/mcp-http.ts handed the adapter's authProvider to the MCP SDK's StreamableHTTPClientTransport and let the SDK route every request, "including the reauthorization it performs on a 401" in the words of the file's own comment. A tools/call answered with 401 could therefore be re-sent by the SDK after a token refresh, below the adapter's dispatch record, with nothing showing that it had gone out twice. The same delegation is at the patch base and at main.1

Why it matters

A retry beneath the execution record repeats a side effect without a new governed decision, which is exactly what the approval flow exists to prevent.

The fix

The transport now wraps fetch. For a tools/call it sends with redirect: "manual", and if the response is not OK it cancels the body and throws McpDispatchBoundaryError (OAUTH_AUTHENTICATION_FAILED for 401, OAUTH_SCOPE_DEMAND for 403 with insufficient_scope, otherwise TRANSPORT_ERROR) before the SDK's session-header or authentication handling can refresh credentials or resend; concurrent calls are inspected per request rather than through shared session state. mcp-http.ts changes 30 lines. Package 09, commit f34ff89: 12 demo-layer files (4 source, 4 test, 4 fixture and documentation), 497 insertions, 23 deletions shared with C07 and P04/issue 58. The package's own text files its "N42" label under transport-permission checks and its one-transmission tests under P04/issue 58; the fetch wrapper described here is what addresses the sealed N42 entry.
